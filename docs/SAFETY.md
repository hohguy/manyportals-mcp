# Safety model

Every write goes to a portal you name. Please read the limits below before you connect a portal whose content you do not control.

ManyPortals relies on routing and credentials.

## What it protects

- **Every write names its portal.** A write must state its target portal. A selected or default portal does not stand in for one.
- **There is no direct write tool.** Every change is drafted as a plan and goes through `draft → validate → execute`, with an `inspect_plan_target` step in between whenever the write touches an existing record or sets a pipeline or stage. In `propose` mode an `approve_plan` step sits before `execute`. In `apply` mode that step is replaced, for the object types you list, by the standing allow-list described under default-deny below. The lifecycle steps are recorded. Nothing requires the target to be inspected before you approve, only before the write runs, so the approval phrase can be asked for on a plan whose target has not been read yet. The assistant issues each of these calls, including `approve_plan`. Whether anything stops it committing a change on its own depends on your client being set to ask before it runs the steps marked destructive. Set it to ask; always-allow removes the last human step.
- **A startup check catches a swapped token wherever you set a hub ID.** When the server starts, it confirms that each token reports the hub ID you configured. A mislabelled or swapped token stops the server from starting, as does a token the server cannot check at all. A read-only portal whose hub ID you leave unknown skips this check, so two portals in that state could have their tokens swapped without the server noticing. Set a hub ID wherever you can.
- **A cross-portal check runs before writes.** The server records the ID of each record it returns to the assistant, against the portal it came from, and refuses a write that reuses an ID it has recorded against a different portal. It is an extra layer rather than a guarantee, and it has limits you should know. It judges only IDs it has recorded. `summarize_pipeline` also records one record ID from each stage that is not empty, without returning it, so an ID you were never shown can still be judged. It compares what it has RECORDED, not what exists in HubSpot: a record that is live in both portals but has been read in only one of them counts as belonging to that one, and a write naming it in the other portal is refused rather than allowed. If that happens, read the record in the portal you are writing to, then draft again. An ID that appears inside a property VALUE of a record you read is not recorded, so copying such a value into another portal is not caught here. The server does check the values you write into fields: if a value is exactly an ID it has recorded against another portal, the write is refused in `apply` mode, while in `propose` mode the plan reports it before you approve and the write is allowed to go ahead. See the limits below.
- **Updates can be read back against the target portal before they run.** `inspect_plan_target` reads the target record in the portal you named and shows a short summary, so you can confirm it is the right record in the right portal. If the record is not there, it is flagged. If the portal's `blockedProperties` hide the fields that would identify the record, the summary can come back holding little more than the ID you supplied, so read what it returns rather than that it returned. It is required before executing a write that touches an existing record, and for a write that sets a pipeline or stage it cannot be waived. Nothing requires it before approval, so you can be asked for the approval phrase on a plan whose target has not been read. For other writes `execute_plan` accepts `skipInspection` and `acceptMissingTargets`. Read those carefully: they are arguments on the execute call, so the ASSISTANT supplies them rather than you, and it can do so on a plan you have already approved. In `apply` mode, for the object types you list, both arguments are ignored. A waiver is recorded when the write goes ahead; if the write is refused for some other reason, the attempt to waive it is not recorded. Only a gate on `execute_plan` in your client prevents it, and that gate is yours to set.
- **Each portal has a default-deny policy.** A write is refused unless its object type and operation are on that portal's allow-lists, and an association's target object type has to be on the allow-list too. In `apply` mode, only the object types you list in `applyAllowedObjects` run without a manual approval. Everything else still needs one. Some properties are refused outright whatever your allow-lists say: `hubspot_owner_id`, `hubspot_team_id`, `hs_all_owner_ids`, `hs_all_team_ids` and `hs_created_by_user_id`, and the reserved stage fields `dealstage`, `hs_pipeline` and `hs_pipeline_stage` wherever they do not belong to the object type being written. Those names are matched as written, so an owner or pipeline property of your own under another name is not recognised. Check such a write yourself before you approve it, and note that in `apply` mode for an allow-listed object type there is no approval step at which to check it. Assign owners in HubSpot directly.
- **Token values stay out of results.** Tokens are read when the server starts and kept in memory for the life of the process. They are sent only as the authorization header of a HubSpot request. Your configured tokens are never placed in a tool result, in the audit log, or in an error message. Text that you or the assistant supply is a separate matter: a value shaped like a HubSpot personal access token or a PEM private key is removed before a result is returned and before an event is stored, and a secret of some other shape is not recognised. At rest, you can keep tokens in an encrypted vault rather than a plain file. A plain token file is still read if one is present, so delete it once its contents are in the vault. The vault is only as private as its passphrase. Your MCP client holds that passphrase, and how it stores and displays it is the client's doing rather than this server's. ManyPortals declares the field sensitive. The Claude Desktop extension showed it in plain text when this was checked on 2026-09-15 and showed it masked on 2026-10-06, so check the client and version you are running rather than relying on either observation.
- **Errors are cleaned before you see them.** Every error raised while a tool is running is replaced by a message this server wrote, and an unexpected one becomes a generic message that carries no response body and no token. A call that does not match a tool's input schema is refused by the protocol layer before the tool runs, and that refusal quotes the argument names you sent.
- **Writes are logged.** A write is recorded before it is sent, and the server refuses the write if that line cannot be stored, so a write that reached HubSpot always left a trace. The line recording the outcome is written afterwards and is best effort: if it cannot be stored, the log shows the attempt with no outcome after it. Either way, check HubSpot. The audit log section below has the detail.

## Where the records go

The server sends its API requests directly to HubSpot and runs no hosted intermediary, so your tokens and records are not relayed through a third party's service.

Your AI client is a separate matter. Whatever records the assistant reads are sent to whichever provider runs that assistant, under that provider's terms, and this server has no say in it. If a portal holds data you may not send to a third party, that decision belongs to you before you connect it here.

## What it does not protect against

The points above govern where a write goes and how tokens are handled. They are not a defence against an AI assistant that has been manipulated.

- **CRM content is untrusted input.** ManyPortals passes CRM content to the AI assistant as it is: notes, email bodies, property values, and so on. That content can contain text that tries to steer the assistant into actions you did not intend. ManyPortals does not attempt to detect or neutralise it, so do not assume that it does.
- **The checks cover IDs and routing, not content.** Routing is enforced: a write goes to the portal it names. The ID check is an extra layer with deliberate exceptions, not a guarantee, and the bullet in [What it protects](#what-it-protects) sets out its limits. Read those rather than this summary: an ID also recorded for the portal you are writing to is accepted, and in `propose` mode a value you were shown and approved goes ahead. Neither check stops the assistant from reading text in Portal B and typing that text into a new record in Portal A. Keeping content separate depends on how the assistant behaves, which rests on the next point.
- **You must control the content in your portals.** The safety story assumes that you wrote, or trust, the records the assistant reads. If a portal takes in content from outside, such as public web forms, inbound email, or support tickets, that content is a way in for injection, and the protections here do not cover it. Running such a portal through this tool is a risk only you can decide to accept.
- **Approval is a human decision, so do not auto-approve.** The exact approval phrase exists so that a person can confirm each write and its target portal. Do not configure your MCP client to approve `approve_plan` or `execute_plan` automatically. In `apply` mode, the per-portal `applyAllowedObjects` list replaces that human pause, so use it only for object types and portals whose content you control.
- **Some data is stored in plain text.** To run the cross-portal check, the server keeps a record of which IDs have been seen in which portal. That file and the audit log are not encrypted, and they are not deleted over time. Their permissions allow your user account only, which assumes those permissions stay intact and that nothing else running as you reads them. Protect the data directory accordingly.

### Where the data directory is, and where to keep it

The server writes the audit log and the ID index **beside your config file**. If your config is at `~/.manyportals/config.json`, the data directory is `~/.manyportals/`. If you moved the config somewhere else, the data follows it there.

On one machine, several copies of the server share that directory safely: each copy writes its own files and never changes another copy's.

A directory synced across machines, such as Dropbox or iCloud, is not safe. The sync can create conflicting copies of a file, and audit or index entries can be lost.

## Sensitive fields

**The scopes on your key decide this, not ManyPortals.** HubSpot requires a sensitive-data scope on the token before it returns the value of a property it has marked sensitive. HubSpot's documentation states that a request naming such a property fails with a 403 error when the token does not hold that scope. [USAGE](USAGE.md) tells you not to grant those scopes, and that instruction is the protection.

If you do grant one, ManyPortals returns those values like any other values. It does not read HubSpot's sensitivity marking and gives a marked field no special treatment.

`blockedProperties` refuses any field whose name matches a pattern you list, per portal, both when reading and when writing. That is the control you set here. It matches the names you supply, not HubSpot's marking, so it protects only the fields you name. See [USAGE](USAGE.md#sensitive-fields).

## About the audit log

**A write is recorded before it is sent.** The server writes an `attempt` line to the log and refuses the write if that line cannot be stored, so a write that reached HubSpot always left a trace. The line recording the outcome is written afterwards and is best effort. So if the process is killed at the wrong moment you can find an `attempt` with no `execute` or `fail` after it. That pairing means "this may or may not have happened, check HubSpot".

**A recorded `fail` is not proof that nothing happened.** If HubSpot accepted the write and the reply was then lost, the log holds an `attempt` and a `fail`, which reads as conclusive and is not. A dropped connection, a timeout, a reply the server could not decode, and some server errors all produce that pairing. Before you send again a write the log calls failed, confirm in HubSpot whether the change you intended is already there. For a create, look for the record. For an update, compare the fields you meant to set: the record existed before the attempt, so finding it tells you nothing. For a write that adds an association, check whether the association is present. A create sent twice leaves two records.

The audit log is useful for day-to-day work, but it is not built for forensics. It is an append-only file, and it is not tamper-proof: a user or program with access to your disk could change it. That is an acceptable trade-off for a self-hosted tool run by one operator. The log holds record IDs, plan IDs, portal keys, timing, and cleaned error messages.

**About tokens in the log.** Your configured tokens are never written to it: they are read when a call is made and never placed in an event. Text you or the assistant supply is a separate matter. A refusal message repeats the value it refused, so an argument shaped like a token used to be written down as given. Values shaped like a HubSpot token or a private key are now removed before an event is stored, and before any result is returned to the assistant.

Each event also records which values the server removed from it, as short handles that stand for the value without containing it. Two things follow. A `(redacted: ...)` note in an event that lists no handle was typed by the caller, not written by the server, so the note alone is not evidence that anything was removed. And the same value produces the same handle every time, so you can tell whether a repeated failure involves one value or many without the value being written down.

Please treat that as a safeguard rather than a promise. It recognises the shapes of a HubSpot personal access token and of a private key. A secret of some other shape, such as a password or an API key from another service, is not recognised and would be stored as written. The log is append-only and this tool cannot edit or delete entries, so the safe habit is not to put secrets into tool arguments at all. If one has already been written, see [Removing something from the log](#removing-something-from-the-log).

### Removing something from the log

The log is append-only on purpose, and this tool has no command that edits or deletes an entry. That is what makes it worth reading afterwards. It also means that if a secret reaches it, the tool cannot take it back out for you.

If that happens, the first thing to do is not the file. **Rotate the credential in the service it belongs to**, which makes the recorded copy worthless. For a HubSpot credential, issue a replacement in HubSpot and revoke the old one, then put the new value in your token file or vault and restart. Use the same kind of credential your setup uses: a Service Key for a new setup, since HubSpot has stopped the creation of new private apps for accounts created on or after 2026-09-28 and ends it for existing accounts on 2026-10-26. That step is enough on its own, and it is the only step that protects you if the file has already been backed up, synced or copied.

If you also want the value gone from disk, the log is plain JSONL: one JSON object per line, in the `audit.d` folder beside your config. With the server stopped, you can edit those files with any text editor. Two things to know before you do:

- **Stop every copy of the server first.** A running copy appends to its own file, and editing underneath it can lose entries.
- **Do not delete the file.** Edit the one line, and leave the rest. Deleting the file destroys the history the log exists for, which is a larger loss than the entry you are removing. If you are unsure, copy the file somewhere safe first.

Some edits are visible and some are not. The entries carry a sequence number per writer, so deleting a line from the middle of a file leaves a gap. Changing a value inside an entry and leaving its number alone does not, and neither does removing the last entry a stopped copy wrote. The edit described above is the kind that leaves no gap. This log is a working record for one operator, not tamper-proof evidence, and the [section above](#about-the-audit-log) says so.
